Snapshots, invalidation, and publication

Three mechanisms answer three questions: what changed, whether the change was about meaning, and how the published view stays consistent.

Implemented Layered snapshot hashing, revision classification, and atomic publication are implemented in the published package and covered by the repository tests.

Layered snapshots

A snapshot hashes three layers separately:

  • Concept layer — the meanings.
  • Notation layer — the local and project symbols.
  • Mapping layer — the relations between them.

Because the layers are hashed independently, a snapshot can say which layer moved. A change of display symbols with untouched meanings shows up as a moved notation hash and an unmoved concept hash, which is a far more useful signal than a single hash of everything.

Semantic and non-semantic revisions

Invalidation classifies a revision before deciding what it forces:

  • A display-symbol-only revision keeps the concept identity. It requires re-rendering, and it is escalated for human review when the old symbol was already active.
  • A semantic revision — a change to definition, scope, assumptions, object type, units, a split or a merge, or a mapping that stops being an equivalence — always creates an explicit downstream invalidation review item.

This is where stable concept identity pays off. Renaming a symbol is a rendering problem. Changing what a concept means is a review problem. Without the distinction, every rename would look like a possible change of meaning, and real changes of meaning would hide among renames.

Atomic publication

The deterministic writer renders a complete view of admitted records, validates that view, and swaps it into place atomically. Two properties follow:

  • A reader never sees a half-written index. Either the previous view is in place, or the new one is.
  • The published view is a function of admitted records. The writer renders; it does not invent meaning, and it cannot introduce a claim that admission never accepted.

Volatile values such as timestamps are excluded from the canonical hashing payload, so re-recording identical semantic content at a different time does not move any layer hash. Drift in a hash means the content actually changed.
