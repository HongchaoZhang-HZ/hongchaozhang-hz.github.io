Derivation Engine documentation

This site documents three Derivation Engine component groups in depth, and it marks the boundary between what is implemented and what is still draft design. It also publishes the bilingual user guide, which describes how a person drives the repository.

Start here: the bilingual user guide

The User Guide group in the sidebar holds the same manual in two languages: English and Chinese. Both editions carry the same fourteen sections, and both are also available as raw Markdown, user-guide/en.md and user-guide/zh-CN.md.

The guide describes the Project-first interaction route in its Agent-native form: the user selects Codex or Claude as the Manager Host, and that Selected Manager is the one window that starts a Project and keeps managing it. Each Project has exactly one Active Manager, a switch requires a durable Handoff, and both Managers share one Project Workspace and Framework Runtime. WezTerm and Herdr are the core live-work surface it schedules, and Obsidian presents complex, structured, durable content. It separates what the five implemented modules do today from the Agent-native deployment that is only proposed, including the two Manager plugins themselves.

The User Guide is not a design component. It is user-facing documentation about driving the repository, and it adds nothing to the three design-component groups below. The repository itself has five implemented modules; this site documents three of them in depth as component groups.

What this documentation covers

These three component groups each have a published, executable test surface, and each has its own section in the sidebar:

Hypothesis Test

The repository component name is Hypothesis Work Unit. It is the smallest independently recoverable unit of work around a single Hypothesis, with a runtime that renders durable Markdown artifacts.

Notation System

The implemented component is the Notation Backbone: a deterministic semantic registry that admits notation only through evidence, concepts, and gated review.

Theorem Derivation

An implemented, test-backed vertical slice that keeps committed theorem state apart from attempts, scoped verification evidence, and the single commit boundary that may advance a checkpoint. It is not a general theorem prover.

The sidebar uses the labels Hypothesis Test, Notation System, and Theorem Derivation. Everywhere else, pages use the repository names Hypothesis Work Unit, Notation Backbone, and Theorem Derivation, because those are the names used by the code and its tests.

System context. These three groups are not the whole repository. The Project Workspace is the upstream project-level module: it owns the project identity, the project's sources and background material, and the links to the other modules. It has no section here, because this site documents the three groups above rather than the project layer. The cross-module diagram on Organization architecture shows where it sits and which of its edges are implemented.

Status boundary

This site is documentation for three component groups. It is not evidence that the full Derivation Engine architecture is settled. Two status labels appear at the top of the pages that need them, and they mean exactly this:

Draft design A contestable design snapshot. It describes intent and boundaries, not behavior you can rely on. The Hypothesis Work Unit design is draft: it defines one DE work unit, not the whole Derivation Engine architecture, and it is not ground truth.

Implemented Behavior that exists in the published code and is exercised by the repository tests. The Notation Backbone is the implemented notation baseline, the Hypothesis Work Unit runtime is the implemented artifact and workspace layer of the draft design, and Theorem Derivation is an implemented vertical slice whose Rounds 01 through 07 are test-backed.

No forward claims. Where a page describes a draft boundary, it says so. The repository now also tracks a notation-first Notation Backbone V2 package alongside the Notation Backbone; this site documents the Notation Backbone and makes no claim about V2 behavior. Theorem Derivation Rounds 08 through 10 are not started, and nothing here claims a general theorem prover. Every implementation described on this site uses the Python standard library only.

Recommended reading path

A newcomer can read the site in this order. Each step takes a few minutes, and each page links to the next one at the bottom.

  1. See how a person drives it. Read the user guide in English or Chinese for the Agent-native route through the selected Codex or Claude Manager, Obsidian, and Herdr, and for the boundary between current capability and next-stage targets.
  2. Understand the work unit. Read Purpose and boundary to learn what a Hypothesis work unit owns and, just as importantly, what it refuses to own.
  3. See who does what. Read Roles and surfaces and Durable artifacts to separate the human-owned decisions from the agent-maintained text and the disposable runtime.
  4. Watch one full pass. The workflow replay shows a single Hypothesis moving from proposal to a completed human TODO in seven frames.
  5. Learn how notation is admitted. Read the semantic chain, then Loading Dock and admission for the gates that stand between a proposal and the registry.
  6. See where results become committed. Read Purpose and boundary, then Organization architecture for the two canonical diagrams that show how the modules and the internal authority boundary fit together.
  7. Follow one claim through the boundary. Committed state and layers, Proof-support paths, and Verification and commit explain what holds, what was merely tried, and what may advance a checkpoint.
  8. Run something. The three CLI pages, Hypothesis Work Unit commands, Notation Backbone commands, and Theorem Derivation commands, list the exact implemented entry commands.

How to read the three components together

The three components answer different questions. The Hypothesis Work Unit asks how one investigation stays recoverable while a human and several agents work on it. The Notation Backbone asks how a symbol earns the right to mean something across the project. Theorem Derivation asks what a project is entitled to treat as established, and keeps that answer behind one commit boundary. They share one habit: durable, reviewable files are the authority, and no agent silently promotes its own output into that authority.

What is implemented in Theorem Derivation and what is still open are stated separately. Rounds 01 through 07 of its vertical slice are implemented and test-backed; Rounds 08 through 10 are not started; the documented cross-module arrows into the Notation packages are manual procedures or missing adapters, and the architecture page draws them as such.

Reading this site offline

Every page here is a static HTML file with relative links. The site needs no build step, no package installation, and no network access: opening docs/index.html from a checkout or serving the docs/ directory with any static file server is enough. JavaScript only adds a theme preference, a narrow-screen sidebar toggle, and remembered sidebar groups; with scripting disabled, every page and every link still works.
