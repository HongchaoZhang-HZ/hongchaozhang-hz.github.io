Organization architecture

Two diagrams answer two different questions: where Theorem Derivation sits among the repository's modules, and where authority runs inside it. Both are drawn from canonical sources that live in the repository, and both are reproduced here exactly.

Implemented Every solid relationship below exists in the published code and is exercised by the repository tests. Dashed relationships are current human procedures or adapters that are not implemented, and they are labelled as such in the diagram itself.

Cross-module system shape

The repository contains five implemented modules with distinct interfaces: the Project Workspace, Notation V2, Notation V1, the Hypothesis Work Unit, and Theorem Derivation.

The Project Workspace is the project-level layer above the rest. It owns the project identity, the project's sources and background material, and the links to the other modules, which is why both of its solid edges point downstream into Notation V2 and the Hypothesis Work Unit. It does not reach committed theorem state: checked theorem-case attachment from a Project Workspace into the A records and B theorem graph is not implemented, so that edge is dashed.

Theorem Derivation does not replace any of the others: its generated Obsidian directory is a read model over an authenticated case report, and the arrows into the Notation packages are not automatic.

Read the dashed arrows literally. A Project Workspace records the project's sources, background, and module links, but nothing attaches a checked theorem case to those records, so the project edge into committed theorem state stays dashed. Notation V2 is a human reference when a theorem case is written; nothing checks the correspondence. No adapter imports a Notation V1 registry snapshot into theorem symbols and roots, and an advanced checkpoint is not exported into the Loading Dock, so an advanced outcome is committed theorem state inside this module, not an automatically admitted Registry record.

Internal authority boundary

The second diagram is the one the module publishes about itself: it is generated into the Project Overview note by the Obsidian projection. It separates committed theorem state from dynamic proposal and verification, and it shows the single arrow that may advance the committed graph.

What the two diagrams agree on

  • A records and the B theorem graph are the committed static state. Nothing else is.
  • The C attempt ledger is dynamic. It holds proposals, attempts, witnesses, and outcomes, and it never says what holds.
  • The verifier plane answers scoped questions. A verifier result changes nothing by itself.
  • The commit automaton is the only advancing interface. It advances B, and it writes the preserved outcome back into C for every other result.
  • Obsidian is a read-only projection of B and C, and human review reaches C for governance only.
  • Live interaction lives in WezTerm plus Herdr and never becomes a second theorem engine.
