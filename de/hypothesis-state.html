State and recovery

A work unit is designed to be resumed. The state names below describe where a unit is, and the recovery rules describe how it gets picked up again.

Draft design State names and recovery rules come from the draft Hypothesis Work Unit design snapshot.

State flow

The flow includes these states:

  • Proposed — an exact ID, title, and statement have been offered.
  • Defined — the human-owned definition exists.
  • Active — the unit has a live interaction workspace.
  • Working — bounded delegated execution is in progress.
  • Verifying — results are being checked before they are reported.
  • WaitingHuman — progress depends on a human answer or decision.
  • Idle — nothing is in flight and nothing is blocked.
  • Recovering — durable state is being read back and missing runtime pieces are being rebuilt.
  • Blocked — something ambiguous or external is preventing progress.

WaitingHuman and Blocked are deliberately distinct. Waiting for the human is a normal, expected state in a unit whose owner holds the decisions; being blocked is not.

Recovery

Recovery follows four rules:

  1. Read durable state first. The Hypothesis, the Handoff, and any active Review Packet are the input. Chat history and terminal scrollback are not canonical state.
  2. Reuse matching roles. If a role is already attached and matches, it is kept rather than duplicated.
  3. Recreate only missing runtime pieces. Recovery is not a rebuild. Disposable identifiers are replaced, and anything still valid is left alone.
  4. Stop on ambiguity. When the durable state does not determine the answer, recovery stops and reports instead of guessing.

Rule four is the reason the other three are safe. A recovery procedure that guesses would eventually invent a decision the human never made, which is exactly the failure the ownership boundary exists to prevent.

What makes recovery possible

Recovery works because the durable artifacts are complete enough to reconstruct intent, and because the runtime metadata is explicitly disposable. Nothing in Runtime/ has to be preserved, so a lost workspace is an inconvenience rather than a loss of work.
