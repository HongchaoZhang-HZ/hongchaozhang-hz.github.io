Verification and commit

Evidence is scoped, checked, and recorded. Only one interface turns it into a new checkpoint, and it refuses far more often than it advances.

Implemented The vocabularies, gates, and preservation rules below exist in the published code. The bundled adapter enumerates declared finite domains, and the external SMT seam reports unsupported because no solver is configured in this repository.

Two vocabularies

The verifier plane reports one of five results:

  • counterexample — a witness against the target was produced;
  • verified-within-scope — a complete search of a declared region, reported together with the region it covered;
  • unknown — the question was not settled;
  • unsupported — nothing configured can answer this question;
  • error — the attempt itself failed.

The commit automaton reports one of four outcomes: advanced, refused, unsupported, and indeterminate. Only advanced builds a successor checkpoint; every other outcome returns the caller's state object unchanged, so the prior checkpoint hash is preserved by construction rather than by a comparison after the fact. Each outcome has its own terminal ledger event, so an unsupported or indeterminate result is never recorded as a refusal.

A bounded search is never promoted into an unbounded proof

verified-within-scope always carries the region that was covered, and the automaton advances only if that region covers the domain the claim is stated over. The bundled case shows both sides of that rule: the same kept formulation advances over a finite declared domain and is indeterminate when it is stated over an unbounded quantity domain.

The witness lifecycle

  1. Raised. An adapter reports a counterexample and the witness it found.
  2. Validated or dismissed. The plane decodes and replays the witness. A successful replay is not by itself a refutation, and a dismissed witness can neither block nor support a checkpoint.
  3. Sustained. Only the commit boundary sustains a witness against the candidate it attacks. An attempt that arrives already sustained is refused at the evidence-linkage gate, and the boundary requires exactly a raised then validated pair in the ledger, bound to the same attempt, target, assignment, and request, before it replays the assignment itself.

Every attempt carries a certificate

A VerificationCertificate names the target, the encoding identity and digest, the premise identities and digest, the tool identity, version and configuration digest, whether the tool actually ran, the result, an evidence digest, and the soundness scope with its rationale. The unavailable-solver path sets tool_available to false, so an absent tool is never presented as having run.

The boundary recomputes what the certificate describes rather than believing it: the encoding identity and digest, the ordered premise identities and digest, the goal, the domain digest against the committed claim domain, the request digest, the tool version and configuration digest, and the evidence digest, and it requires the certificate identifier to be the deterministic identifier of its attempt.

Admissibility and precedence

  • A sustained counterexample refuses.
  • A malformed or errored attempt offered as support refuses.
  • unknown is indeterminate; unsupported is unsupported.
  • Only admitted verified evidence whose scope covers the claim domain enters the successor checkpoint certificate. Everything else stays auditable in the ledger with no mathematical force.

Verification along a named proof

A candidate that would advance a statement must name the exact proof-support path its evidence adjudicates. The certificate carries the same identity, the boundary requires the two to agree, and a candidate or certificate that names none is refused: the boundary never selects a proof after the fact. A promoted statement records every path it has been verified along in verified_path_ids, so a second verification along a different proof accumulates rather than replaces.

Gate order at the commit boundary

state-authenticity
ledger-projection
candidate-freshness
structural-admission
premise-establishment
obligation-discharge
evidence-linkage
counterexample-check
evidence-admissibility
verifier-scope-sufficiency

Every evaluated gate is recorded in the result, so a refusal always names the gate that stopped it.

What the boundary does not claim to check

An adapter configuration rewritten together with both of its digests leaves an attempt internally consistent, and the boundary holds no adapter to contradict it; that case is refused by the content-bound ledger instead. A submitter who also controls the append-only ledger is outside this model. Only statement targets can advance at the boundary: assumption and obligation targets can be attacked but not promoted.

No solver is installed, emulated, or invoked by this repository. The external SMT seam owns the encoding, the injected runner, and the answer taxonomy, and with no configured runner it reports unsupported rather than guessing.
